## Persistence and behavior

- Each setting is a single atomic Firestore batch. Sharing writes invitations/removal requests together with the sender's tracking records. Labels writes membership changes and any new-label actions together. A rejected batch leaves none of those changes persisted. Creating a new label first establishes its private editor prerequisite; that alone creates no visible label.
- Save waits for acknowledgment and confirmed state refresh before returning. After a committed write, a failed refresh retries only refresh/cache completion, not the write. Offline submissions remain open until reconnection. No acceptance or immediate access-revocation claim is made when a request is merely sent.
- Request type and outcome distinguish Shared, Invitation pending, Removal pending, and Invitation declined. Pending rows are read-only. Incoming removals are acknowledged automatically rather than waiting for mouse movement. A re-invitation retains the last known list name.
- Drafts are scoped to individual settings. Remote label memberships merge when untouched; conflicting edits require an explicit choice. Permission loss and remote deletion disable Save while preserving readable input.
- Deletion is confirmed separately and removes the document from both participants' navigation. The two-user story verifies reload. Deleting a label leaves source lists/tasks intact. This action does not claim permanent erasure of task/history documents.
- Request IDs at the cached timestamp boundary prevent a same-second reload from dropping newly created lists. Existing caches without this metadata retain the previous replay policy until refreshed. Concurrent list listeners consult current replay boundaries so refreshing a saved setting does not replay its actions twice.
