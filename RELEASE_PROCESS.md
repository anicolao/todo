# Release process

Production deploys are release-only. An ordinary commit to `main` runs the normal checks but does
not deploy. To release, generate a version-only pull request, review its preview and checks, and
merge it.

## Generate a release candidate

1. Open **Actions → Generate Release PR → Run workflow**.
2. Select `patch`, `minor`, or `major`. Use `patch` unless the release intentionally needs a larger
   version increment.
3. Open the generated `Release vX.Y.Z` pull request from the workflow summary.
4. Review its CI and CLI results and use the preview link posted on the pull request.
5. Merge the pull request when the candidate is ready for production.

The generator starts from the current `main`, runs `npm version` without creating a local tag,
and commits only `package.json` and `package-lock.json` on `release/vX.Y.Z`. It also creates or
updates the `release` label and applies it to the pull request.

GitHub deliberately prevents a pull request created by `GITHUB_TOKEN` from recursively triggering
`pull_request` workflows. The generator therefore dispatches CI, CLI Gate, and the existing PR
preview workflow explicitly. They run against the release branch's exact head commit, so their
results belong to the generated pull request just as normal PR checks do.

Only one open release PR is allowed. If a candidate is abandoned, close its pull request and
delete its branch before generating another candidate. Do not add application changes to a release
branch; land those on `main` first and generate a fresh release candidate.

## What deploys

Every successful CI run for a commit on `main` asks the production workflow to classify that
commit. The workflow deploys only when all of these conditions hold:

- exactly one pull request labeled `release` is associated with the commit;
- its title is exactly `Release vX.Y.Z` and its branch is `release/vX.Y.Z`;
- it changes only `package.json` and `package-lock.json`;
- both files contain the same new version generated by npm;
- the version is exactly one patch, minor, or major increment from the commit's first parent; and
- CLI Gate for the same `main` commit has passed.

An ordinary `main` commit leaves the deploy job skipped. A version change that does not satisfy the
release contract fails closed and does not deploy. This makes a generated and merged release PR the
only path to production; merging unrelated work never causes a deployment.

After Firebase deployment succeeds, the workflow creates both:

- an immutable semantic version tag, such as `v0.1.47`, plus a GitHub Release with generated notes;
- a timestamped deployment tag under `deploy/prod/` for operational history.

Tags and the GitHub Release are written only after production deployment succeeds, so they certify
what was actually deployed rather than merely what was proposed.

## Failure and retry behavior

If a release PR check or preview fails, fix the underlying problem on `main`, close the candidate,
and generate a new one. Release branches are intentionally version-only.

If checks on the merged commit fail, production is not deployed. Re-run the failed `main` check
after correcting any transient issue; a subsequent successful CI completion will classify the same
commit again. If the production workflow itself fails during preflight or deployment, use GitHub's
**Re-run failed jobs** action. The semantic tag is idempotent and must either be absent or already
point at that release commit.

## Local commands and native shells

`npm run deploy:preflight` and `npm run deploy` remain available for diagnosis, but they are not the
release mechanism. The former local `npm version` hook and `bin/packagedist` helper were removed
because changing a version must never deploy or push from a developer's machine as a side effect.

This process deploys the hosted application and Cloud Functions. App Store, TestFlight, and Android
store submissions remain separate native-shell release processes even though those shells load the
hosted application at runtime.
